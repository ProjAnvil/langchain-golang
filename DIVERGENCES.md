# Divergences from Python LangChain/LangGraph

Deliberate design decisions where this port does not mirror Python. Each entry states why. Anything not listed here aims for parity; file an issue if you find a gap.

## Never planned

- **LangGraph Platform / Server / Studio / CLI** — commercial product lines, out of scope for an OSS port.
- **Local transformers models** — the Go ecosystem has no comparable runtime; use API providers (or ollama for local serving).
- **Command-Send / remaining_steps** — superseded upstream patterns whose Go equivalents (explicit routing, run control) already exist.

## Deliberate design differences

- **Cache short-circuit middleware** — Go's `cache` middleware short-circuits identical requests instead of Python's instrumentation-only behavior; Go idiom favors explicit memoization points.
- **Blank-import provider registration + shim re-exports** — partner packages self-register via `init()` and top-level `langchain/` shims re-export the stable surface, mirroring Go stdlib plugin patterns rather than Python's explicit imports.
- **SQL toolkit read-only guardrails** — langchain-community's SQLDatabaseToolkit executes whatever the model sends; the Go sqltoolkit rejects anything but a single SELECT/WITH statement (comments stripped before analysis, write keywords rejected in the statement body) on both `sql_db_query` and `sql_db_query_checker`, since an LLM with write access to a database is a footgun the port refuses to ship. The checker also validates via the database planner (EXPLAIN) instead of an extra LLM call, `sql_db_schema` accepts empty input to describe all tables, and sample-row values are tab-joined (upstream comma-joins row values but tab-joins headers).
- **Failed-write retry continues instead of re-running (#9235)** — when a DeltaChannel write fails, Python never saved the observing checkpoint, so a retry re-runs the failed task ("running it again reruns the task", cba111d8d). Go's per-task writes must anchor on the checkpoint persisted before them (every saver requires the checkpoint row), so the failed run's checkpoint is instead repaired with a full snapshot blob of its delta channels and the retry CONTINUES from it: the failed task is not re-executed. Identical final state for deterministic graphs; for nondeterministic or side-effecting nodes the task's second execution never happens. See checkpoint_sink.go's #9235 header comment for the mechanism.
- **ID-less messages-mode node outputs re-emit per scan (#9463)** — Python's `StreamMessagesHandler._emit` mints a uuid4 ONTO an ID-less message (pregel/_messages.py:126-127), so the streamed chunk and the checkpointed state share one ID and later scans dedupe it. Go never mutates a node's returned messages (the #9275 ID-stamping contract replaces values by copy only), and minting an ID on just the emitted copy would desync the streamed ID from the applied/persisted write, so the run-scoped ledger treats empty IDs as never-dedupe: such a message re-emits on every scan that sees it. The canonical path is unaffected — messages written to a messages delta channel are #9275-stamped before emission — so the divergence only reaches messages stored ID-less on non-messages channels.
- **Nested-invoke stream isolation keys on identity, not config provenance (#9458)** — Python drops inherited messages/tools handlers whenever a child is not run as a task of the caller: its own `thread_id`, `checkpoint_ns`, or `checkpoint_id` — including a runnable call that re-supplies the SAME values in its own `configurable`, which replaces the caller's config and thereby drops its `task_id`. Go's `Options` cannot distinguish an explicitly re-supplied value from the caller's own (there is no config object identity to compare provenance through), so `stripNestedInvokeCarriers` drops only when the child's `ThreadID` or `CheckpointID` DIFFERS from the enclosing run's: a child explicitly re-supplying the caller's identical values keeps streaming into the caller's stream, where Python would drop it.
- **Draining a fresh-identity nested invoke stops its caller (#9458 × #9281)** — Python's fresh-identity child (own thread/configurable) replaces the caller's config, so `CONFIG_KEY_RUNTIME` — and with it `parent_runtime.control` — is absent and the child mints a fresh `RunControl`: draining it stops only the child. Go threads the enclosing run's control through the context (the `executionMeta` value survives the #9458 carrier strip, which only removes stream carriers), so a fresh-ThreadID/CheckpointID child inherits the caller's RunControl and its drain stops the caller too (the child's `GraphDrainedError` aborts the parent run). Exotic on purpose; same-namespace children inherit in both implementations.
- **Messages-delta ID stamping is constructor-bound, not identity-based (#9275)** — Python's `ensure_message_ids` gates on `spec.reducer is _messages_delta_reducer` (imported-identity check); Go function values are not comparable, so `channels.NewMessagesDeltaChannel` records the binding and `IsMessagesDelta` reports it. A hand-built `NewDeltaChannel(BatchFromReducer(MessagesReducer), ...)` folds byte-for-byte the same way but is never ID-stamped — language-forced, and Python has the mirrored hole: a private copy of the reducer (e.g. deepagents') is not the imported object and also goes unstamped. Upstream 1.2.19 additionally tier-2-stamps message objects written to OTHER delta channels; the Go port deliberately stops at the canonical messages delta channel (wave-4 spec D3) — messages stored ID-less on non-messages delta channels keep their pre-#9275 behavior.
- **Unresolvable `Options.CheckpointID` errors instead of starting empty** — when a pinned checkpoint id resolves to nothing, Python falls back to a synthetic empty checkpoint (`CheckpointTuple(..., empty_checkpoint(), {"step": -2}, ...)`, _loop.py:1844-1849) and runs from scratch under the same config; Go fails the invoke ("no checkpoint found"). Pre-existing: a wrong checkpoint id is almost certainly caller error, and silently forking the thread from empty state hides it.
- **`__tools` node metadata requires bound registration (#9449)** — Python's `get_graph()` duck-types every node's callable for `tools_by_name`; Go nodes are `func` values converted at `AddNode`, so there is nothing to duck-type. Export metadata therefore comes only from `AddNodeWithBound`/`prebuilt.AddToolNode` registrations: a plain `AddNode("tools", ToolNode(node))` executes identically but exports no `__tools` metadata.
- **Notification metadata merge keeps-first on leaf conflicts (#41540)** — Python's `merge_dicts` sums differing ints and raises TypeError on float/bool leaf conflicts; `MergeRuns` has no error channel, so `lc_data` leaf conflicts keep the first value (type-conflict rules for `lc_source`/`lc_data` likewise replace-or-keep instead of raising — see `core/messages/notification.go`). Equal string/list leaves also short-circuit where Python concatenates/appends (merge_dicts has no general equality pre-check — only an `index` string with an lc_ prefix and equal `id`/`output_version`/`model_provider` strings skip), and Python's last-wins rule for int `index`/`created`/`timestamp` is not mirrored. No known consumer accumulates notification numbers.
- **RawPayloadHandler exemption does not cross nested Manager boundaries** — the payload-policy marker (`core/callbacks/payload_policy.go`) type-asserts each handler in a manager's own handler set; a `callbacks.Manager` composed into another manager as a handler is not itself a RawPayloadHandler, so handlers that are exempt inside the nested manager observe scrubbed payloads through the outer policy. The known protected handlers (messages bridge, usage aggregation, StreamEvents collector) are registered at the top level and unaffected.
- **Default tool-error handling stays catch-all** — Python langgraph 1.1.1+ default `handle_tool_errors` converts only argument-binding errors (`ToolInvocationError`) inside `_execute_tool_sync` and re-raises every execution error (the run fails unless a wrap middleware converts it); Go's `tools.DefaultHandleToolErrors` keeps the older convert-everything default so a failing tool yields an error ToolMessage and the run continues — zero behavior change for existing setups except the ToolRetryMiddleware flip noted below (controller ruling 2026-11-02). `agents/middleware.ToolErrorMiddleware` (#38781) is the explicit opt-in to Python's posture (convert only the errors your handler selects, propagate the rest via `tools.UnhandledToolError`). Note the conversion itself now runs at ToolNode's runOne level, OUTSIDE the wrap chain (mirroring `_run_one`), so wrap middleware observe raw tool errors — with a wrapper installed, errors that a wrapper lets escape (e.g. an HITL edit naming an unregistered tool) are now default-converted where they previously failed the run, matching Python's `handle_tool_errors=True` mode. `tool_end` StreamEvents are emitted by the tools node from the ordered post-conversion outcomes (not from the wrap chain, which only observes raw errors): default-converted and middleware-converted error `tool_end`s carry the converted content and `status=error`, a declined error (conversion bypassed, run failing) emits no `tool_end` — and in a mixed batch where one sibling's error is declined, the completed siblings' `tool_end`s are suppressed with it (the node fails before emitting), and concurrent siblings' `tool_end`s follow the call order, not the completion order — Python emits no `on_tool_end` for failing tools at all (its tool runs record `on_tool_error`), so the error-path `tool_end` payload and the call-order emission timing are Go-specific shapes with no upstream analog. A second, intended flip from the same move: ToolRetryMiddleware users inside create_agent's always-installed wrap chain previously never saw real tool failures as errors — the conversion ran inside the chain, so retries never fired and failures surfaced as the default-converted message; now retries actually fire, and "continue"-mode failures carry the retry-formatted text. Intended per ruling R2 (the layering move): this mirrors Python's `_run_one`, where retry middleware has always seen raw errors — effectively a bugfix for the previously-dead retry path.
- **ToolErrorMiddleware observes binding errors too** — Python's `on_error` sees only tool *execution* errors (argument-binding/validation errors become error ToolMessages inside `_execute_tool_sync`, within the wrap chain, so they never reach it); Go's `core/tools` and `langchain/tools` expose no uniform binding-vs-execution error marker (verified: both surface binding failures as plain errors from `Tool.Invoke`), so the middleware's OnError receives both. Handlers that must distinguish them need tool-specific error types.
- **Non-standard block `index` stays inside Value** — Python lifts a non-standard block's `index` to the block top level (#40213 area); Go's `NonStandardContentBlock` has no Index field and keeps `index` inside `Value`. The caller-map mutation bug Python fixed there never existed in Go (the escape hatch clones via `cloneMap(stripType(m))`).
- **Interrupt IDs are `node-N`, not xxh3 hashes** — Python 1.2.20 keys an interrupt's id by `xxh3(ns)` plus the answer count (#9589); Go mints `nodeName-counter` per call, which already gives every interrupt in a task its own id (the shared-id stale-answer bug class #9589 fixes never existed in Go). Checkpoint files are not cross-SDK shareable anyway (existing divergence), so id format mismatch has no interop impact.
- **Strict resume map detection** — Python treats a resume dict as an id map only when every key is an xxh3 interrupt id; Go has no xxh3 ids, so any `map[string]any` resume is treated as a resume map (same as Go's non-strict path).
- **Strict resume on superseded checkpoints** — Python skips the strict check when the addressed checkpoint was superseded; Go skips it on pinned (`CheckpointID`) resumes, the only path where supersession occurs (mirrors the exit-path gate in checkpoint_sink.go).
- **`EventToolStart/End/Error` callback kinds are defined but never emitted** — Go tool executions surface as chain events; the tool-kind mapping exists only in the StreamEvents/LangSmith projection tables. (Found while auditing #41660.)
- **`JSONParser` text path has no message visibility** — Python checks refusals in `parse_result`'s ChatGeneration branch; Go's `[]outputs.Generation` carries no message (no covariance), so message-level refusal checks live in `language.InvokeStructured` and partner StructuredCaller paths instead.
- **Strict resume RemoteGraph drop-list** — Go has no RemoteGraph (existing backlog), so Python's `CONFIG_KEY_STRICT_RESUME` forwarding drop does not apply.
- **ModelRefusalMiddleware's omit marker** — Python's `omit_payload` returns an empty dict; Go's TracePolicy for refusal/router middleware replaces inputs with `{"omitted": true}` so the scrub stays visibly intentional.

## deepagents (Python deepagents v0.7.38 → `deepagents/`)

Divergence register for the deepagents MVP port (Tiers 1-4: backends,
FilesystemMiddleware, SubAgentMiddleware, CreateDeepAgent). D1-D14 are the
planned scope decisions; the parked items below them accumulated through the
per-task reviews. Implementation plan:
`docs/superpowers/plans/2026-11-14-deepagents-port.md`; per-task reports
under `.superpowers/sdd/2026-11-14-deepagents-port/`.

- **D1 summarization** — the existing Go `SummarizationMiddleware` is reused with a single-call model-backed default summarizer; upstream's `create_summarization_middleware(model, backend)` backend-offload superset is not ported.
- **D2 profiles** — the harness-profile system (`_profile`, profile middleware/materialization) is skipped.
- **D3 async subagents** — `async_subagents` skipped; `ParentNotifier` consequently not ported (dead code without them).
- **D4 optional middleware families** — skills, memory, rubric, `_video`, `_blob_offload`, `_message_eviction`, `_overflow_clip`, `_prompt_caching`, and unsupported-content handling are skipped.
- **D5 sandbox/execute** — `SandboxBackendProtocol` and the `execute` tool are skipped (CreateDeepAgent registers no execute tool); sandbox/langsmith/context_hub/store/composite backends skipped; protocol `upload`/`download` not ported.
- **D6 model required** — the model is a required argument; upstream's deprecated default-model path (anthropic/google-genai) is not ported — `CreateDeepAgent(nil)` fails at the general-purpose compile.
- **D7 glob matcher** — `wcmatch` (GLOBSTAR + BRACE) replaced by a hand-rolled matcher: `*`, `?`, `[...]` per segment, `**` spanning separators, no brace expansion (`a.{x,y}` matches literally).
- **D8 subagent namespace metadata** — the ToolMessage artifact's `checkpoint_ns` is omitted (no namespace plumbing in the Go tools node).
- **D9 forked subagents** — not ported (fork-mode notes and `_FORKED_SUBAGENT_TOOL_NOTE` absent from the task tool description).
- **D10 subagent runs are non-pausable** — no checkpointer threaded into subagent invocations and interrupts do not bubble to the parent run: an interrupted subagent answers the task call with the pinned tool text `subagent interrupted (not resumable in this port)`. ThreadID derivation is `task:<toolCallID>` without a parent prefix (the parent ThreadID is unreachable from the tool surface).
- **D11 micro-defaults** — tool-result eviction (20k char) not ported; grep `max_count` default 1000 ported; fs-interrupt `when`-predicate scoping not ported (a derived interrupt entry covers EVERY call of the tool — strictly more conservative than upstream); tool-allowlist checks on middleware-provided tools not ported.
- **D12 PatchToolCallsMiddleware skipped** — valid-but-dangling tool-call repair gap: the Go agent loop repairs invalid calls only, as before.
- **D13 same-batch `files` collisions** — write-tool + write-tool in one model batch errors with the ported `_parallel_file_mutation_error` literal (wired at `FilesystemMiddleware.WrapToolCall`, batch-sibling detection through the batch AI message in the request state); only the `task` + write-tool pair folds, last-write-wins per key at the tools node's Command application (`applyToolNodeCommands`), where upstream merges through the channel reducer. The agent-level fold is whole-value per batch: `applyToolNodeCommands` (create_agent.go:3412-3424) overwrites the entire `files` value with each later Command, so an uncontested task-written file key can be shadowed by a later write snapshot in the same batch where upstream's channel reducer preserves it; the contested-key behavior (later Command wins) is correct and pinned by the Task 9 fold test. Since D15 the channel itself also commits replacements, making the whole-value fold the end-to-end semantics (one Overwrite-wrapped snapshot per superstep).
- **D14 messages reducer** — the Go agents' existing messages reducer is reused; upstream deepagents compiles `messages` with a DeltaChannel. Semantics are equivalent for this port's invoke surface.
- **D15 files channel commit (snapshot replacement via Overwrite)** — the `files` state key commits as snapshot REPLACEMENT: the port's filesystem tools (`filesCommand`) and the task writeback (`SubAgentMiddleware.invokeTask`) wrap each full post-mutation snapshot in `channels.Overwrite`, and the `binaryOperator` channel replaces its stored map wholesale, so a deleted key stays deleted (Spec §4). Upstream instead uses a delta-merge channel (`_file_data_reducer` with explicit tombstones). Semantics are equivalent for this port's pipeline because every superstep commits exactly one full snapshot — same-batch Commands pre-fold at `applyToolNodeCommands` (D13), which is also required since the channel accepts only one Overwrite per super-step — and the StateView folds all of a tool's mutations internally before the commit. `MapMergeReducer` stays registered as defense for UNMARKED (hand-built) writes, which overlay key-by-key.

Parked items (per-task review findings, disclosed rather than fixed):

- **FIFO/device acceptance** — `FilesystemBackend` Read/Edit accept non-regular, non-directory files; upstream `is_file()` reports them as not-found (Go checks only `IsDir`; reading a FIFO with no writer blocks).
- **Symlink-walk inconsistency** — Glob/Grep directory walks filter on `DirEntry.Type().IsRegular()`, excluding symlinks-to-files that upstream's `is_file()` follows; Ls follows symlinks (`os.Stat`), so the port is internally inconsistent on this edge.
- **Partial-match-on-abort** — Grep walk-abort and Glob context-deadline failures return an error and discard matches gathered so far; upstream returns the partial results flagged truncated.
- **Ls sort key** — entries sort by bare name; upstream's filesystem backend sorts by path-with-trailing-`/` key (order differs only for a dir/file pair sharing a name prefix at the `.`/`/` boundary). Upstream itself is divergent between its backends here (see the state-glob note).
- **Typed traversal error in glob** — upstream glob's `_resolve_path` ValueError escapes uncaught and surfaces via the middleware's generic handler; Go returns a typed `*backends.Error` — a benign improvement.
- **State-glob sort** — upstream's State backend sorts glob results by `modified_at` descending (tie-unstable); the Go port sorts lexicographically on BOTH backends — mutually consistent and matching upstream's filesystem backend, divergent only from upstream's state backend.
- **maxCount==0 semantics** — the Go backend treats `maxCount <= 0` as unlimited; upstream Python `max_count=0` (int, not None) returns immediately truncated-empty. The middleware always passes the 1000 default, so only direct backend callers see the difference.
- **Truncation flags dropped** — `GrepResult.truncated` and glob `truncated`/`truncation_reason` are absent from the pinned result shapes; caps are enforced but truncation is unreportable.
- **Grep line clipping dropped** — upstream clips each `content`-mode matched line to `GREP_LINE_CHAR_LIMIT` characters; the Go grep returns lines unclipped (match-count caps still apply).
- **LsEntry size dropped** — upstream's byte-size computation per entry is not carried.
- **Unknown output_mode fallback** — upstream's Literal rejects unknown `output_mode` values at validation; the Go tool silently falls back to `files_with_matches`. (`max_count` validation is ported: `gt=0` is enforced at the tool layer — zero or negative returns an error — and an omitted `max_count` yields the 1000 default; see `newGrepTool`.)
- **Double-prefix glob-fail text** — a non-timeout glob backend failure renders `Error: glob failed: {e}` wrapping the backend's own error text, so an already-prefixed backend error reads with both prefixes.
- **Brace-rule inertness** — with no brace expansion (D7), a brace pattern in a rule path or glob matches literally rather than being rejected; it is inert, never destructive.
- **ASCII rstrip set** — `taskResultContent` rstrips with the ASCII set `" \t\n\r\v\f"`; Python `str.rstrip()` also strips Unicode whitespace (NBSP etc.). Parity footnote.
- **Subagent tracing metadata dropped** — upstream stamps `ls_agent_type="subagent"` and `lc_subagent_tool_call_id` on subagent runs; the port's direct graph invoke also skips the agent-name run tag (cosmetic, tracing only).
- **Silent empty-content on a missing messages key** — upstream raises when a compiled subagent's result lacks a `messages` key; the port's type assertion degrades to empty content (practically unreachable: `CompiledSubAgent.Agent` is an `*agents.Agent`).
- **Subagent stack trims** — the Tier-3 compiled subagent stack is FilesystemMiddleware (only when `Backend` is set, with no permission rules) + ModelRefusalMiddleware + the spec's own middleware: no summarization, no PatchToolCalls, no profile extras/skills, no `default_tools` inheritance (spec.Tools is the complete list), no UnsupportedContentMiddleware, no per-subagent HITL. The assembler's auto-added general-purpose subagent carries the parent's caller tools and middleware (upstream graph.py:918) but NOT its own FilesystemMiddleware over the shared backend with the parent's permissions. Consequence: the auto-added GP's verbatim description ("…has access to all tools as the main agent") overstates file access — the compiled GP carries no fs tools, so delegated file work fails at binding; callers wanting full parity supply their own `general-purpose` spec with `Backend` (plus their own permission gating). Follow-up recorded as future work: subagent permission inheritance (`SubAgentSpec.Permissions`) is a Tier-3 API gap — upstream graph.py:856-860 gives the GP subagent the parent's FilesystemMiddleware permissions, and the spec type currently has no Permissions field. Supplying your own FilesystemMiddleware in `spec.Middleware` alongside a non-nil `Backend` fails loudly on the duplicate instead of upstream's name-splicing.
- **langgraph binop zero-seed parity (outside deepagents scope)** — Go's `BinaryOperator` channel, like Python's, seeds the FIRST value without applying the reducer (Python's binop.update consumes `values[0]` before its Overwrite-detection loop; it does NOT seed a zero value). One deliberate Go deviation, added with D15: an Overwrite-wrapped first write seeds with the marker's INNER value where Python would store the marker struct itself — storing the wrapper would leak it into `Get`/`Checkpoint` and every later merge's type assertions (pinned by `TestBinaryOperatorSeedsOverwriteInnerValue`). Full-snapshot updates keep the raw seed's stored form correct either way, but the underlying langgraph seed behavior otherwise remains Go-side and affects any dual-form reducer.

## Deferred (upstream-triggered)

- **deepagents** — upstream is pre-1.0 (0.7.x) with an unstable API; the MVP Tier 1-4 subset (backends, FilesystemMiddleware, SubAgentMiddleware, CreateDeepAgent) is ported — see the deepagents section above for its divergence register; everything beyond that tier is re-evaluated when upstream reaches 1.0.
- **AWS Bedrock provider, RemoteGraph client** — demand-triggered; both are on the backlog.

## Notable per-adapter behaviors

- **SSRF NAT64 prefixes** — langchain core #41151 unwraps the embedded IPv4 from both NAT64 prefixes (`64:ff9b::/96` and `64:ff9b:1::/48`) and checks it; the Go port blocks both prefixes wholesale (stricter: NAT64-tunneled public IPs are also denied).
- **Decisions/TypeSafe classifier scope** — the OpenAI Decisions client (openai 1.7.0 #41125) and TypeSafe classifier (langchain-typesafe 0.0.1a3) do not resolve the LangSmith gateway (`LANGSMITH_*` env fallbacks unimplemented; the Go port has no gateway support yet — missing-key messages drop the gateway hint sentence) and do not attach usage to the ambient run tree (no current-run accessor exists; usage travels on the response type only).
- **Classifier question serialization order** — both clients serialize the `questions` mapping by sorted name (Go maps are unordered); Python relies on dict insertion order. Wire-visible only for multi-question requests.
- **AutoMode trace policy** — wrap-tool-call middleware have no trace-policy installation point in `create_agent` (only wrap_model_call layers do), so the openai/typesafe AutoMode risk gates run without the omit-payload policy Python applies (#41125); tool arguments in their traces are not redacted. ModelRouter (wrap_model_call) implements omit-payload as upstream. The same gap covers wrap-tool-call middleware that declare their own payload policy upstream, e.g. ToolErrorMiddleware's `process_inputs=omit_payload` (#38781/#40098): its tool-call arguments are equally unredacted.
- **AutoMode vs ModelRouter image handling** — upstream's own asymmetry preserved: openai AutoMode keeps every image (base64 and hosted-URL) in its with-images variant, while its ModelRouter keeps only base64 images; the Go port matches both behaviors.
- **Blocked ToolMessage status** — Python marks blocked tool calls with `ToolMessage(status="error")`; the Go `Message` has no status field, so AutoMode writes `AdditionalKwargs["status"]="error"` instead.
- **typesafe ModelRouter error semantics** — Python crashes (`StopIteration`/`KeyError`) when no human message is present or the routing answer is missing; the Go middleware returns explicit errors (openai's ModelRouter keeps Python's nil-route continue behavior). The router also stores `model_route` as a JSON-native map rather than a pydantic model, and identifies itself as `langchain-typesafe-go/0.0.1` in User-Agent.
- **typesafe 400 overflow classification** — Go's shared `ModelErrorKindForStatus` sniffs context-overflow markers in 400 bodies for every provider, including TypeSafe (Python's typesafe client maps 400 to plain invalid-request); harmless but broader than upstream.
- **boolean Choice values** — openai Decisions boolean choice options stringify lowercase (`"true"`), Python renders `"True"`; only visible for bool-valued choices.
- **exa transport** — REST-direct against api.exa.ai (no exa_py SDK); parameter surface matches langchain-exa 1.1.0, and tool failures surface typed lcerrors instead of Python's `repr(e)` strings.
- **nomic adapter scope** — remote text embeddings only: empty `Model` defaults to `nomic-embed-text-v1.5` (Python requires it), `dimensionality` supported, but no local/dynamic inference mode and no `embed_image`/vision; Go adds explicit task_type validation, fast-fail on a missing key, and a defensive `ErrSchemaValidation` when the API returns no embeddings for a query.
- **Internal-call filtering mechanism** — Python langchain 1.4's `internal_call_metadata()` + `InternalCallTransformer` mark and drop middleware-internal model calls from the `run.messages` projection and raw event log via stream transformers (#39252); the Go port uses an unexported context token (`callbacks.WithInternalCall`/`IsInternalCall`) checked at the messages-bridge and StreamEvents collector — unspoofable without transformer infrastructure, same filtering behavior (messages mode + StreamEvents chat-model events; values/updates unaffected).
- **`interrupt(response_schema=)` does not validate resume values** — Python builds a pydantic TypeAdapter from the schema and raises ValidationError on a mismatched resume value (langgraph 1.2.13); the Go port surfaces the schema to consumers (run results, GetState, durable serde round-trip) but performs no validation on resume, keeping the graph runtime free of a schema-validation dependency. Consumers render forms/validate client-side.
- **Subgraph delta-channel reads through the parent graph** — `parent.GetState(childNS)` unwraps delta snapshot blobs (proto-independent) but does not reconstruct sentinel-only child delta channels: the parent holds no registry of subgraph channel protos. Read sentinel child channels through the child graph compiled with the shared saver instead (run-path hydration already resolves the caller's saver, Python #8538's core scenario).
- **Task paths are dispatch positions, not Python path tuples** — Python's `task_path` (`task_path_str(path)`, e.g. `"~0000000001, 0000000000"`) encodes the trigger path through the task tree; the Go executor has no path tuples, so `Write.TaskPath` carries the task's zero-padded dispatch index within its planning superstep (`"0000000001"`). Within one checkpoint every pending write belongs to a single superstep, so the index preserves the same invariant savers replay by (`(task_path, task_id, idx)`, Python #8544): replay order == live dispatch order. Pathless `""` writes (graph input, update_state) sort first, matching Python.
- **Exit-mode pause anchoring needs a sort-before exit write path** — Python's #9114 anchors pause-time exit-durability writes on the run's START checkpoint; the Go port anchors them on the pause checkpoint itself (kept from the v0.11.1 exit-anchor checkpoint-ID reservation work), where they share the checkpoint with the pause superstep's direct writes. Earlier-superstep exit writes therefore use a Go-only `"!"`-prefixed step-qualified task path (`exitDeltaEarlyPath`) that sorts before every real dispatch path — the mirror image of Python's sort-after `"~~"` late paths (`exitDeltaLatePath`), which the port also uses for supersteps after the anchor superstep.

- **anthropic `tool_choice=none`** — the Messages API has no `none` type; binding fails loudly instead of silently misrouting (bind no tools instead).
- **anthropic effort tracing (#41536)** — the fix half of #41536 surfaces constructor `effort`/`reasoning_effort` through Python's `_identifying_params` (LangSmith trace defaults); Go has no identifying-params mechanism, so the resolved level is observable only via `ChatModel.Effort()` and the request payload. The payload/validation half (output_config emission, profile-gated adaptive-thinking default, opus-5 conflict) is ported in full.
- **anthropic adaptive-thinking default also constrains sampling (#41536)** — when the injected adaptive default fires (effort set, no explicit thinking, profile declares xhigh support), Go keys `applyThinkingConstraints` on "thinking present in the payload" and forces temperature=1 / drops top_p and top_k exactly as for an explicit thinking config; Python sets the default thinking and leaves the caller's sampling params untouched (its only sampling-param pops are fable-5-specific).
- **anthropic in-place tool-change forwarding stays profile-gated** — Python's adapter never consults `mid_conversation_tools` when formatting system content: the leading run is formatted with `preserve_tool_changes=True` unconditionally (chat_models.py:741-747, #40758) and so is every in-place mid-conversation system turn (`_format_in_place_system_messages`, chat_models.py:701-713); the profile's only formatting gate is `mid_conversation_system_messages` + `_previous_turn_allows_system` on in-place *placement*. The Go port matches the leading run (tool-change blocks forward for every model, profile or not) and the placement gating, but keys tool-change *forwarding* on the in-place path to the `mid_conversation_tools` profile key (`inPlaceSystemTurns`, chatmodel.go): on a model whose profile allows mid-conversation system messages but not tools (claude-sonnet-5 — the one model upstream data marks `mid_conversation_tools = false`), an in-place system turn's tool_addition/tool_removal blocks are dropped with the tool-change drop warning (`warnToolChangeBlockDropped`) where Python sends them and lets the server reject. Kept deliberately (controller ruling 2026-11-02): the key exists precisely to mark which servers accept mid-conversation tool changes, so the port surfaces the unsupported case at the client instead of burning a round-trip.
- **anthropic beta headers set the header only** — `WithBetaHeaders` merges flags into the `anthropic-beta` request header without the `?beta=true` query flag; Python routes ANY betas-bearing payload through the SDK's beta namespace (`/v1/messages?beta=true`). Go adds the query flag only when the request itself requires betas (tool-change system blocks, the `updates` thinking display, `user_profile_id`, or an `output_config` `task_budget`). Likely wire-equivalent — the header and the flag enable the same beta surface — noted for completeness.
- **anthropic streaming terminal chunk carries no `stop_details` in chunk metadata** — the terminal chunk carries only `stop_reason`/`stop_sequence`; `stop_details` lands solely in the final aggregated message's `ResponseMetadata`. Upstream (chat_models.py:2510-2511) also places `stop_details` in the chunk-level metadata.
- **gemini adapter scope** — targets the Gemini API backend (generativelanguage.googleapis.com, API-key auth) via the official genai SDK only; the Vertex AI backend (Python's `use_vertexai` path) is not covered, and `GOOGLE_GENAI_USE_VERTEXAI` is deliberately ignored (backend pinned) so the adapter cannot be silently rerouted.
- **gemini streaming usage metadata** — the API reports cumulative token counts on every SSE response; Python subtracts previous usage to yield per-chunk deltas, the Go adapter instead surfaces usage only on the terminal chunk (plus a terminal usage-only chunk when counts arrive after the finish chunk), keeping aggregating consumers correct with a single attachment point.
- **gemini `ParallelToolCalls`** — the Gemini API has no parallel-tool-calls payload field; the bind option is accepted and dropped (allowedFunctionNames is already fully determined by the tool-choice mode).
- **gemini streaming tool-call wire shape (#41257)** — tool-call args stream as whole blocks (content-block-start carrying the finalized call + content-block-finish), not as `tool-call-delta` args slices like openai/anthropic: the genai SDK (v1.71.0) delivers each `FunctionCall` with a complete parsed `Args` map, and its `PartialArg` incremental type is documented "not supported in Gemini API", so there is no per-slice payload to forward. Python's google-genai adapter is in the same position (each chunk carries the full serialized args as one delta); the semantic result — a complete call per chunk — is identical.
- **ollama streaming tool-call wire shape (#41257)** — same whole-block shape as gemini: ollama's chat stream schema delivers each tool call's `function.arguments` as one complete payload (JSON object, string, or Python literal) per chunk, with no fragment streaming in the API, so there are no args slices to retag as `tool-call-delta`. Consumers still see `content-block-start`/`content-block-finish` pairs carrying the complete call.
- **chunk-bridge wire indices are source-preserving, not renumbered (#41257)** — Go's two chunk bridges (`core/language/stream_events.go`, `langchain/agents/stream.go`) preserve SOURCE-side block indices (per-key stable, collision-free among non-text blocks) and pin text to wire index 0, whereas upstream #41257's `_compat_bridge` renumbers sequentially from 0 in first-seen order (text is an ordinary keyed block; there is no shared-0 case). Observable only in index VALUES — provider indices that do not start at 0 or arrive out of first-seen order keep their own numbers instead of Python's dense 0..n sequence; consumer assembly is unaffected either way, since per-key stability is what pairing and ordering rely on. Kept deliberately: renumbering is pure churn against Go's pre-existing honor-the-source-index behavior, with regression risk and no consumer-visible gain.
- **MCP adapter scope** — mirrors langchain 1.4.0's `langchain.mcp` blueprint on mcp-go: elicitation bridges to LangGraph interrupts on the modern MRTR protocol (transport-independent) while legacy server-initiated elicitation is only supported for in-process servers (remote transports cannot safely unwind — upstream has the same limitation); tool discovery caching is presence-based (mcp-go exposes no server TTL hints); per-connection protocol negotiation (mcp-go) instead of MCPConfig's single era; structured results surface as `ToolArtifact` (the Go tool pipeline is text-first, there is no content_blocks channel on ToolMessage); destructiveHint defaults follow the MCP spec's conservative default (true), so un-annotated remote tools are HITL-gated when `InterruptOnConfigs` is enabled.
- **TracePolicy handler scoping** — upstream #9486 scopes payload policies BY TYPE: only non-streaming `BaseTracer` handlers record processed payloads; usage handlers, stream collectors, and `astream_log`'s handler get the real ones. Go has no tracer type system, so the port uses the inverse, language-forced rule: handlers under a policy are scrubbed by default and opt out by implementing `callbacks.RawPayloadHandler`. The known protected handlers are opted out (langgraph's messages bridge, `callbacks.UsageMetadataHandler`, `runnables`' StreamEvents collector); any other non-tracer handler placed under a policy is scrubbed until marked.
- **TracePolicy processor failures** — for a processor that errors mid-transform, upstream records the untransformed payload; the Go port drops the payload (fail-closed) since the feature's motivation is PII/compliance.
- **Error-handler abort semantics** — a failed superstep's successful handler outcomes are not committed (Go commits writes at superstep end vs Python's per-task `put_writes`), so a resume after a sibling-task failure re-runs an already-succeeded handler; effects must therefore be idempotent.

## Known limitations

- **`ToolRetryMiddleware.WrapToolCall` still routes RetryOn-declined errors through handleFailure (backlog)** — the tool-side retry middleware keeps the old shape: an error `RetryOn` rejects still goes to `handleFailure`, so `on_failure="continue"` swallows it into a ToolMessage. This differs from `ModelRetryMiddleware` (aligned in wave5: non-retryable errors propagate immediately, mirroring Python model_retry where `RetryOn=False` bypasses `on_failure`). To be aligned separately.

- **Exit-mode time travel across an anchored start checkpoint — fixed on the resume paths; one new-turn corner remains** — under exit durability, a run that resumes from checkpoint P anchors its accumulated delta writes on P under synthetic step-prefixed task IDs (`exitDeltaTaskID`/`exitDeltaLateTaskID`, `langgraph/graph/delta_helpers.go`) while P's `Next` still plans the very tasks that ran — never their real IDs, so a run whose final checkpoint fails to save does not leave the resumed task looking done (both ports agree; Python's `_put_exit_delta_writes`, `_loop.py`). A later resume loading such a P now recognizes those writes by their synthetic IDs' embedded superstep (`parseExitDeltaTaskID`): steps after P's own are the consuming branch's work, so `resumeFromTuple` (resume.go) excludes them from the hydration seed and seals their channels (forced snapshot via `deltaOverwriteChs`, folded into every save by `saveCheckpoint`/`flushExit`) — a pinned (time-travel) resume re-runs the planned tasks against P's own state, each write applying exactly once, and the fork's stored state never replays the abandoned branch's writes. This is Python's own semantics (#8548: a resume addressed by `checkpoint_id` reruns and force-snapshots every pending-write delta channel, `_loop.py:1011-1015`; loaded writes reapply did not hand back are sealed at `_loop.py:708-722`; loaded pending writes never hydrate live state — reapply pairs only real task IDs, `_loop.py:833-845`), not the earlier `_written_task_ids`-reapply reading: the synthetic IDs are load-bearing on both sides. Writes at or before P's step are the exit-pause path's own early-anchored state (`putPauseCheckpointExit`) and stay seeded. Remaining corner: a NEW TURN (fresh input) on a head that carries such stale writes — a failed flush — still seeds them into its live state (the new-turn branch seeds the head's pending writes by design, graph.go); reads are shadowed by that branch's #9235 force-snapshot, but the live run folds the abandoned work in, where Python's new-turn run would exclude it. `GetState` of the anchor checkpoint itself still folds its own pending writes (anchored ones included), exactly like Python's fork-base reads (#8548).
